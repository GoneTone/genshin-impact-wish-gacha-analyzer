## 一、背景與目標

鳴潮版已有「從其他平台匯入」（WuWa Tracker）。原神版要比照，差別只在平台：

- **genshin-wish-export** → 不做它自己的格式，改成直接實作 **UIGF**，涵蓋 genshin-wish-export 與其他輸出 UIGF 的工具。
- **paimon.moe** → 用它的 **Excel 匯出檔**。

使用者的核心要求：**不同來源的資料要能混合合併，絕對不能多出不該有的記錄，也不能少掉該有的記錄。** 典型情境：

- 先匯入第三方資料，之後才用 App 抓官方資料（或反過來）。
- 官方資料中間有一段空檔（使用者超過 API 保留期限沒抓），用第三方資料補上。
- 單抽與十連混在一起，十連內有多筆同星級的記錄。
- 同一份檔案重複匯入、多份第三方來源交錯匯入、雲端同步在多台裝置之間來回。

### 非目標

- **UIGF Excel（v2.2 的 UIGF.W）**：v2.3 起已被規範移除，現役工具不再產生，不支援。
- **genshin-wish-export 自己的 Excel 格式**：不是 UIGF，不支援。
- **UIGF 中其他遊戲**（`hkrpg`、`nap`）：不讀。`hk4e_ugc`（千星奇域，即頌願）要讀，見〈二〉。
- **捏造資料的偵測**：第三方檔案裡手動捏造、且落在官方沒有涵蓋時間的記錄，任何程式都無法判斷真假；本 App 自己的備份檔同樣可能被竄改。已知限制，不處理。
- **時區換算 UI**：UIGF 規範要求 `time` 保留抽卡網頁的原始字串、不做轉換；paimon.moe 實測也是原樣保存伺服器時間。兩者都直接沿用，不提供時區選項。

## 二、來源格式

### UIGF（JSON）

以 2026-11-25 使用者提供的 genshin-wish-export v0.12.1 實際匯出檔（v3.0 與 v4.1 各一份，同一批 1155 筆）以及 uigf.org 規範為準。

| 版本 | 結構 | 版本欄位 | UID／語言 |
|---|---|---|---|
| v2.0～v2.4 | `{info, list}` | `info.uigf_version` | `info.uid`、`info.lang`；記錄本身也可能帶 `uid`、`lang` |
| v3.0 | `{info, list}` | `info.uigf_version` | 同上；實測記錄本身沒有 `uid`、`lang` |
| v4.x | `{info, hk4e: [{uid, timezone, lang, list}]}` | `info.version` | 每個 `hk4e` 元素一個帳號，可有多個帳號 |

- 記錄欄位：`uigf_gacha_type`、`gacha_type`、`id`、`item_id`、`name`、`item_type`、`rank_type`、`time`、（`count`）。
- v4.2 規範的必填只有 `uigf_gacha_type`、`gacha_type`、`item_id`、`time`、`id`；`name`、`item_type`、`rank_type` 是選填。
- 檔案的 `gacha_type` 保留 `400`；`uigf_gacha_type` 把 `400` 併成 `301`。匯入時存 `gacha_type` 的 `400`（見〈三〉、〈十八〉）。
- 實測檔案依 `id` 由舊到新排列；本 App 存檔是由新到舊。
- 遊戲 1.3 版以前的記錄沒有 `id`（舊工具匯出的 UIGF 可能出現）。

**頌願（`hk4e_ugc`，v4.2 起）**：2026-11-25 決定一起匯入。

- 結構與 `hk4e` 相同（每個元素一個帳號：`uid`、`timezone`、`lang`、`list`），記錄格式則對應官方 `getBeyondGachaLog`：名稱在 `item_name`，類型在 `op_gacha_type`（值為 schedule 級 ID，如 20011／20012／20021／20022，與 1000／2000 不同），另有 `schedule_id`。欄位確切定義以實作當時的 uigf.org 規範為準。
- 存檔卡池 key 與 `gachaType` 比照 App 抓官方頌願的方式（`GachaRecord.fromApiJson` 用查詢的 `1000`／`2000`）：`op_gacha_type` 要對應回 `1000`／`2000`，對應表在實作時從規範與官方 API 確認。
- 頌願記錄有官方 `id`，合併走〈五〉的規則（實際上就是 `id` 聯集）。
- 頌願不做語言轉換（沿用現有：`GachaLanguageConverter` 只處理非頌願記錄）。
- 同一帳號同時出現在 `hk4e` 與 `hk4e_ugc` 時合併成一個帳號。

**版本判斷**：先讀 `info.version`，沒有再讀 `info.uigf_version`，格式 `v{major}.{minor}`。

- 主版本號 2、3、4：照常解析；小版本號比已知更新也照常解析（同一主版本只往上加東西：v4.1 加崩鐵卡池，v4.2 加頂層 `hk4e_ugc`（千星奇域，即 App 的頌願），都不改既有欄位）。
- 主版本號大於 4：整份拒絕，訊息說明版本較新、請更新 App 或改用 v4 匯出。
- 兩個欄位都沒有，或結構對不上：視為不是 UIGF 檔案（`ForeignBundleException`）。

### paimon.moe（Excel）

以使用者提供的實際匯出檔（`Information` 分頁 Version 4）為準。

- 分頁：`Character Event`、`Weapon Event`、`Standard`、`Beginners' Wish`、`Chronicled Wish`、`Banner List`、`Information`。
- `Information` 的 A1 是 `Paimon.moe Wish History Export`，用來判斷是不是 paimon.moe 檔案；不是就 `ForeignBundleException`。
- 卡池分頁欄位（以標題列名稱定位，不依欄位順序）：`Type`（`Character`／`Weapon`）、`Name`（英文）、`Time`、`⭐`、`Pity`、`#Roll`、`Group`、`Banner`、`Part`；Character／Weapon Event 另有 `Guaranteed`。只用到 `Type`、`Name`、`Time`、`⭐`、`Part`，其餘忽略。
- `Part` 為 `Wish 2` 代表 `gacha_type` 400。匯入存成 `400`，與修正後的官方抓取一致（見〈十八〉）。
- `Banner List` 分頁忽略。
- `Time` 儲存格實測是文字 `yyyy-MM-dd HH:mm:ss`（只是格式設成日期樣式）；也要能吃 Excel 日期數值，以不帶時區的方式轉回同樣格式的字串。
- **沒有 UID、沒有官方 `id`**。
- 同一秒內的列順序與官方 `id` 順序一致（實測 699＋290＋166 筆，逐筆比對星級與類型順序完全相同）。

分頁對照：

| 分頁 | `gacha_type` | 存檔卡池 key |
|---|---|---|
| Character Event | 301，`Part`＝`Wish 2` 時 400 | `301` |
| Weapon Event | 302 | `302` |
| Standard | 200 | `200` |
| Beginners' Wish | 100 | `100` |
| Chronicled Wish | 500 | `500` |

## 三、欄位對映

`GachaRecord` 欄位：`id`、`uid`、`gachaType`、`name`、`itemType`、`rankType`、`time`、`lang`。

| 欄位 | UIGF | paimon.moe |
|---|---|---|
| `id` | `id` 符合官方格式（19 位數字、首位非 0）就沿用；否則產生替代 `id`（見〈四〉） | 一律產生替代 `id` |
| `uid` | v4：`hk4e[].uid`；v2／v3：記錄的 `uid`，沒有則 `info.uid` | 使用者在選帳號對話框選的 UID |
| `gachaType` | `gacha_type`（保留 `400`）；缺少時用 `uigf_gacha_type` | 依分頁與 `Part`（`Wish 2` → `400`） |
| `name` | `name`；缺少時見下方〈名稱與語言〉 | `Name`（英文） |
| `itemType` | `item_type`（在地化字串，原樣保存） | `Type`（`Character`／`Weapon`，與官方 en-us 字串相同） |
| `rankType` | `rank_type`；缺少時見下方〈星級〉 | `⭐` |
| `time` | `time` 原樣解析 | `Time` 原樣解析 |
| `lang` | 記錄的 `lang` → 帳號的 `lang`（v4 `hk4e[].lang`／v2～v3 `info.lang`） | `en-us` |

存檔卡池 key 由 `gachaType` 決定，`400` 放進 `301`，其餘相同。

**名稱與語言**：

- 有 `name` 也有 `lang`：直接用，之後交給既有的 `GachaLanguageConverter` 轉成資料語言（現有匯入流程已會在合併後呼叫）。
- 缺 `name`，或有 `name` 卻找不到任何 `lang`：用 UIGF 字典（`https://api.uigf.org/dict/genshin/{lang}.json`，內容是「名稱 → `item_id`」，反轉後由 `item_id` 查名稱）以資料語言對應的字典補名稱，`lang` 設為資料語言。
- 字典抓不到（離線、伺服器錯誤）或查不到某個 `item_id`：**整份拒絕**並說明原因，不跳過任何一筆。
- 轉不了資料語言的記錄照樣保留，只是顯示原語言名稱。

**星級**：UIGF v3 起 `rank_type` 是選填，UIGF 字典也沒有星級。缺少時（2026-11-25 決定）用 HoYoWiki 查：

- 先依〈名稱與語言〉取得名稱，再用既有的 HoYoWiki 搜尋（`HoYoWikiFetcher`）找到條目，從條目的 `filter_values`（角色為 `character_rarity`，武器的對應群組實作時確認）解析出星級。
- 同一個 `item_id` 只查一次；能用既有的 HoYoWiki 快取就不重抓。
- 任何一筆查不到或解析不出星級 → **整份拒絕**並說明需要網路或查不到的物品，不跳過。
- 查詢在匯入確認之前完成，期間顯示既有的進度樣式（實作決定），不可中途關閉的視窗依 CLAUDE.md 設 `showCloseButton: false`。

**未知卡池類型**：`gacha_type`（或分頁）不在 100、200、301、302、400、500 之內 → **整份拒絕**並列出類型。鳴潮遇到未知 `cardPoolType` 是跳過並寫 log；原神因「不能遺失」改成拒絕。

**必要欄位缺失或格式錯**（`time` 解析不了、星級不是 1～5 等）→ **整份拒絕**（`FormatException`），log 帶出第幾筆／第幾列。

## 四、替代 `id`

沒有官方 `id` 的記錄產生替代 `id`：

```
"0" + yyyyMMddHHmmss（14 碼，取自 time）+ 同一秒內序號（2 碼，00 起）+ "00"
```

- 共 19 碼，與官方 `id` 等長，字串比較等於數值比較。
- 首位 `0` 就是標記：`id.startsWith('0')` 即替代記錄。官方 `id` 前 10 碼約為 unix 秒數，首位永遠非 0。**不改存檔格式、不加欄位。**
- 序號依來源檔在同一卡池、同一秒內的順序。paimon.moe 的列順序已驗證與官方一致；UIGF 依檔案順序。同一秒超過 99 筆 → 整份拒絕（實際上一秒最多 10 筆）。
- **同一筆抽卡不論匯入幾次、從哪個平台匯入，替代 `id` 都相同**，所以重複匯入靠既有的 `id` 去重就不會重複。
- 替代 `id` 一律小於所有官方 `id`。還沒更新的舊版 App 若拿到含替代記錄的資料，抓取時的停止點仍會落在官方記錄上（另見〈七〉的 `schema_version`，舊版其實會直接被擋下）。

## 五、合併規則（核心）

鳴潮用「時間＋物品＋星級＋數量」當指紋，做序列對齊（SCS）再把每個指紋的數量封頂為兩份來源中較多者。原神改成**以「卡池 key＋同一秒」為單位整組比對**，保證相同：**結果不少於任一份來源，也不多於任一份來源。**

改用整組比對的理由：原神時間精確到秒，同一卡池的同一秒只可能是一次抽卡動作（單抽 1 筆或十連 10 筆；使用者資料實測只有這兩種組）。不需要名稱，也就不受名稱語言或轉換失敗影響。

### 規則

對每個卡池 key（`301` 含第二個角色活動祈願的記錄），把本機（local）與傳入（incoming）的記錄依 `time` 分組，每一秒：

1. **有官方記錄**（任一邊有 `id` 不以 0 開頭的記錄）→ 結果是兩邊官方記錄依 `id` 取聯集；同 `id` 保留本機那筆，本機 `lang` 為空而傳入的不為空時回填 `lang`（沿用現有 `_mergeRecordsById` 行為）；本機 `gachaType` 為 `301` 而傳入為 `400` 時改成 `400`（〈十八〉）。這一秒的替代記錄全部捨棄。
2. **兩邊都只有替代記錄** → 取筆數較多的那一組。筆數相同時用與來源無關、可重現的規則挑一組：把每組記錄依 `id` 排序後，比較 `(lang, name, itemType)` 串成的字串，取較小者（實作決定確切序列化方式，但必須與合併順序、裝置無關）。這樣兩台裝置各自持有 paimon 版與 UIGF 版時，雲端同步會收斂到同一份，不會來回覆寫。**不同來源的記錄永遠不會混在同一秒。**
3. 只有一邊有這一秒 → 直接採用。

最後依「`time` 由新到舊，同 `time` 依 `id` 由大到小」排序。

這套規則放在 `BannerStorage.mergeWith` 底下的共用函式（取代現在的 `_mergeRecordsById`），**匯入備份、雲端同步、第三方匯入、抓官方資料全部走同一個函式**，並且要具冪等性。

### 必須成立的性質（全部要有測試）

1. 本機官方記錄在任何合併中都不會被刪除或修改（`lang` 回填與〈十八〉的 `400` 修正除外）。
2. 同一份資料合併兩次，結果與合併一次相同。
3. 合併順序不影響結果：例如 paimon→官方、官方→paimon、UIGF→paimon→官方的各種排列，結果完全相同。
4. 每個「卡池＋秒」的筆數 = 有官方時等於官方筆數，否則等於兩邊較多者，**絕不相加**。
5. 只有官方記錄的資料，用新規則合併的結果與現在的 `id` 聯集完全相同（順序也相同）。

### 2026-11-25 用真實資料模擬的結果

用使用者三個檔案（Python 拋棄式模擬，未進版控）驗證上述規則，以下情境結果都與官方 1155 筆完全一致：

| 情境 | 結果 |
|---|---|
| 先 paimon 再官方 | 1155 筆，全部是官方記錄 |
| 先官方再 paimon | 1155 筆 |
| paimon 匯入兩次再抓官方 | 1155 筆 |
| 官方缺 2026-03～06，用 paimon 補 | 官方 856＋補上 299 |
| paimon 只有前半、官方只有後半，重疊一個月 | 接起來，重疊不重複 |
| paimon 某次十連少一筆，再抓官方 | 那一秒整組換成官方 10 筆 |
| 三份來源 6 種合併順序 | 結果完全相同 |

實作的測試要用**匿名化、自行建構的 fixture** 重現這些情境，不可把使用者的真實檔案放進版控。

## 六、抓官方資料的流程調整

`gacha_fetcher.dart` 的 `fetchBannerWithMerge`：

1. **停止點**：現在用 `existing.first.id`。改成「既有記錄中最新的官方 `id`」（略過替代記錄）；沒有官方記錄就是 `'0'`（抓到 API 盡頭）。否則最新一筆是替代記錄時會停錯地方。
2. **合併**：現在直接 `[...fresh, ...existing]`，前提是新記錄都比既有的新。有替代記錄時不成立（替代記錄可能比最新的官方記錄還新）。改成用〈五〉的共用合併函式合併 `existing` 與 `fresh`。
3. 空 `lang` 回填（頌願 API 不回傳 `lang`）的行為不變。第三方匯入的祈願記錄一定有 `lang`；頌願記錄可能沒有（UIGF 未提供時存空字串），之後抓官方資料會依現有規則用網址的 `lang` 回填，頌願不做語言轉換，只影響顯示用的語言標記。
4. 規則只會用官方記錄取代同一秒的替代記錄，不刪其他記錄，所以抓到一半失敗也不會少資料。

這是電腦版與 Android 共用的程式，兩個平台都要有測試鎖住現有行為（只有官方記錄時結果與現在相同）。

## 七、排序與依賴 `id` 順序的程式

卡池內排序從「`id` 由大到小」改成「`time` 由新到舊，同 `time` 依 `id` 由大到小」。2026-11-25 檢查使用者本機兩個帳號共 1792 筆，`id` 順序與時間順序零反轉，所以對既有資料不會改變顯示順序；用測試鎖住「只有官方記錄時兩種排序結果相同」。

需要檢查、必要時改成依時間的地方（實作時再 grep 一次全部 `id` 比較）：

- `gacha_fetcher.dart`：停止點（〈六〉）。
- `banner_storage.dart`：`_mergeRecordsById` 的排序與 dartdoc「依 id 降序」。
- `gacha_repository.dart` 的 `_seedLangFromData`：用 `id` 找最新記錄，替代 `id` 永遠最小，改成先比時間。
- `timeline_entries.dart`：只用 `id` 判斷相等，替代 `id` 唯一，不受影響（確認即可）。

## 八、`schema_version`

**規則：寫進檔案的版本號，是讀懂這份內容最低需要的版本。**

- 版本 1：現有格式。
- 版本 2：含有替代記錄（任一帳號任一筆 `id` 以 0 開頭）。
- 讀取端可接受的最高版本改為 2（`AccountsBundle.fromJson` 現在只擋「比自己新」的版本，較舊的版本本來就能讀）。
- 寫入端由固定常數改成依內容計算：有替代記錄寫 2，否則寫 1。
- 未來新增版本 3 時，getter 取所有條件中最大的版本；若改動是每份檔案都會用到的，條件恆成立，等同整體升版。
- dartdoc 寫明這條規則，並列出每個版本代表的內容。

效果：只有用過第三方匯入的帳號，舊版 App 讀到時會顯示既有的「請更新 App」；其他人照常同步。**鳴潮沒有處理這一點**（它的版本 2 是當初移植時改的，第三方匯入沒有升版）。

匯入時遇到版本 2 的備份走同一套合併規則，不需要額外處理。

## 九、重疊期間對不上的提醒

paimon.moe 沒有 UID，選錯帳號會把別人的記錄整批加進來，而且沒有復原功能；時區錯開也會讓整批對不上。合併規則不會因此出錯，但會加進不該有的資料，所以在確認畫面提醒，**只提醒、不拒絕**。

判斷（每個要匯入的帳號分別算）：

- 取本機官方記錄的「卡池＋秒」集合，與傳入記錄的「卡池＋秒」集合。
- 重疊期間 = 兩邊時間範圍的交集。
- 在重疊期間內，傳入的組數 N、其中能對到本機官方同一「卡池＋秒」且筆數相同的組數 M。
- **N ≥ 10 且 M ≤ N ÷ 10** 時提醒。

已知的誤判：官方資料在重疊期間內有大段空檔、第三方資料剛好只補在空檔裡時，也會提醒。代價只是多一次確認，使用者按「仍要匯入」即可。

只用於第三方匯入；本 App 自己的備份匯入與雲端同步不做這項檢查。

### `PlatformImporter`

新檔 `lib/services/platform_import.dart`，介面比照鳴潮，差異：

- `lib/services/importers/uigf_importer.dart`：處理〈二〉〈三〉的 UIGF 規則；v4 可能產出多個帳號。

- 兩者共用替代 `id` 產生函式（放在合併規則同一處或獨立小檔，實作決定）。

### 新增套件

`pubspec.yaml` 目前沒有讀 xlsx 的套件，新增一個（例如 `excel`），實作時再確認版本、授權與 Windows／Android 都可用。

## 十五、測試計畫

- **合併規則**（`banner_storage` 的共用函式）：〈五〉的五個性質逐一測試；〈五〉的模擬情境以匿名 fixture 重現；只有官方記錄時與舊行為逐筆相同。

## 十七、與鳴潮的差異

| 項目 | 鳴潮 | 原神 | 原因 |
|---|---|---|---|
| 合併演算法 | 指紋序列對齊（SCS）＋數量封頂 | 「卡池＋秒」整組比對 | 原神一秒就是一次抽卡，且存檔沒有語言無關的物品 id |
| 合成／替代記錄的標記 | 合成 `resourceId` | `id` 首位 `0` | 原神記錄沒有 `resourceId` |
| 抓取流程 | `mergeOrderedRecords` 錨點對齊 | 停止點改成最新官方 `id`＋共用合併 | 原神抓取靠官方 `id` |
| 未知卡池類型 | 跳過並 log | 整份拒絕 | 使用者要求不能遺失 |
| `parse` 輸入 | `String` | bytes | paimon.moe 是 xlsx |
| 指定 UID | 無（檔案自帶） | paimon.moe 要選帳號 | paimon.moe 沒有 UID |
| 重疊對不上提醒 | 無 | 有，只提醒 | paimon.moe 沒有 UID，選錯帳號的風險 |
| `schema_version` | 未因第三方匯入升版 | 有替代記錄時寫 2 | 避免舊版用 `id` 聯集合出重複 |

## 十八、先修：第二個角色活動祈願（400）

2026-11-25 寫設計時發現的既有問題，決定在同一個分支、第三方匯入之前，當作獨立任務先修。

### 現況

- 2026-05-14 的 `a4e51cd`（修頌願解析）讓 `GachaRecord.fromApiJson` 一律用查詢的卡池類型覆寫 `gachaType`。祈願的第二個角色活動祈願因此從 `400` 變成存 `301`。
- 在那之前抓的記錄存的是 `400`。使用者本機資料：角色活動祈願 1035 筆中，2025-12 的 40 筆是 `400`，其餘是 `301`。
- 畫面上沒有任何地方處理 `400`：`gachaTypeFor('400')` 查不到，時間軸會直接顯示「400」當卡池名稱，顏色也走未知卡池的預設值。保底門檻剛好和角色活動祈願相同（90／10），所以統計不受影響。
- 卡池 key 一直都是 `301`，所以合併規則不受這個欄位影響。
- 官方祈願歷史頁與主流工具都是「400 與 301 同一個分類、共用保底，但每筆記錄保留 400 並標成角色活動祈願-2」：官方祈願頁 bundle `itemTypeNameMap` 的 `400`（術語表已收錄）、genshin-wish-export（`src/gachaType.json`）、paimon.moe（`Part`＝`Wish 2`）、UIGF（`gacha_type` 保留 400）。

### 修法（2026-11-25 決定，比照官方與主流工具）

- **分類與保底不變**：400 的記錄仍放在卡池 key `301`，保底連續計算，門檻與 301 相同。
- **抓取**：祈願（`getGachaLog`）改回存 API 回傳的 `gacha_type`；頌願（`getBeyondGachaLog`）維持用查詢的 `1000`／`2000` 覆寫（`op_gacha_type` 是 schedule 級 ID，不能直接存）。
- **合併修正**：同一 `id`、本機 `gachaType` 為 `301` 而傳入為 `400` 時，改成 `400`。使用者下次抓資料，一年內被存錯的記錄會自動改正；更早的抓不回來，維持原樣。雲端同步兩台裝置也會收斂到 `400`。
- **顯示**：`gachaTypes` 加入 `400`，名稱用官方「角色活動祈願-2」（新 ARB key，各語言照術語表與官方 `itemTypeNameMap`），保底規則與 301 相同，分類為祈願。顏色預設與角色活動祈願相同，實作後給使用者看過再定。
- **依 `record.gachaType` 彙總的地方**（例如 `timeline_horizontal.dart` 依 `gachaType` 計數後只列 `gachaTypes` 裡的卡池）：400 要算進角色活動祈願，不能因為多了一個類型就漏算或多出一列。實作時 grep 所有讀 `gachaType` 的地方逐一確認。
- **測試**：抓取存 400、頌願仍覆寫、合併修正 301→400、時間軸與表格顯示官方名稱、彙總不漏算；電腦與手機版面都看過。
